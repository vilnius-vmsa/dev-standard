# Vilnius dev standard: documentation

This skill runs the methodology in appendix G of the standard (Lithuanian, binding): https://vilnius-vmsa.github.io/dev-standard/priedai/dokumentacijos-rengimo-metodika. Where this skill and appendix G differ, appendix G wins.

Every sentence you write in documentation is a **claim**. A claim is done when you have opened the file it cites and seen the behaviour it states.

## Rules for every mode

1. Describe current behaviour. Plans and intentions go into an ADR with a status, or a coverage row marked "Not yet".
2. Point at code by path and symbol: `src/Service/StorageService.php`, method `bind()`. Line numbers go stale; leave them out.
3. Link to the one place a fact lives (setup in README, big picture in `docs/architecture.md`) and keep each fact in one doc.
4. Write terse, checkable sentences; prefer tables and lists.
5. Verify every claim against the file it cites before you keep it.
6. Domain claims (what a system is for, who uses it, how external systems relate) that you inferred from names, comments or commit messages go on the **Facts to confirm** list. A person confirms them. Names mislead: agents have read two names for one system as two systems.
7. Document quirks as the code behaves today. Describe security gaps as observed behaviour with a code pointer, at the level a maintainer needs to fix them.
8. Write references to docs that do not exist yet as plain text; the checker rejects dead links.
9. When the code proves another doc wrong, fix that doc in the same change.
10. Use the language the repository's docs already use. For new docs: English, with Lithuanian domain terms kept in the glossary.

## Documentation layout

| Artifact | Path | Template | Requirement |
|---|---|---|---|
| README | `README.md` | (existing) | 3.8.4 |
| Agent guide | `AGENTS.md` | [AGENTS.md](templates/AGENTS.md) | appendix G.6 |
| Docs index and coverage table | `docs/README.md` | [docs-README.md](templates/docs-README.md) | appendix G.2 |
| Architecture | `docs/architecture.md` | C4 L1 and L2 | 10.2.1, 3.8.1 |
| Glossary | `docs/glossary.md` | [glossary.md](templates/glossary.md) | appendix G.5 |
| Subsystem deep dive | `docs/<subsystem>.md` | [deep-dive.md](templates/deep-dive.md) | 3.8.2 |
| ADRs | `docs/adr/NNNN-<title>.md` | https://vilnius-vmsa.github.io/dev-standard/priedai/adr-sablonas | 10.4 |
| API spec | e.g. `docs/openapi.json`, generated by a repository command | | 10.2.2, 3.3.1 |
| Deployment, operations, runbooks | `docs/deployment.md`, `docs/runbooks/` | https://vilnius-vmsa.github.io/dev-standard/priedai/runbook-sablonas | 10.2.3, 9.8 |
| Docs check in CI | `.github/workflows/docs-check.yml` | [docs-check.yml](templates/docs-check.yml) | appendix G.8 |

The **coverage table** in `docs/README.md` maps each area to its doc and its **source paths** (the folders and files that doc describes). Update mode finds affected docs through that column, so keep it exact.

A subsystem needs a deep dive when a new developer could not understand it in 30 minutes from the code alone (3.8.2).

## Choose the mode

- A code change in this branch touches documented behaviour → **update**.
- The repository has no `docs/README.md` with a coverage table, or you are asked to write initial docs → **bootstrap**.
- You are asked whether the docs are correct or complete → **audit**.

## Bootstrap

1. **Inventory.** List the existing docs (README, `docs/`, wiki exports, API spec), the top-level folders, the CI workflows and the build and test commands. Note every existing claim that the code contradicts.
2. **Scope.** Propose to the user: which subsystems get deep dives, which gaps become coverage rows, which language. When a person is available, wait for their agreement.
3. **Write**, verifying each claim as you go, in this order: `docs/glossary.md`, `docs/architecture.md`, deep dives, `docs/README.md` with the coverage table, then `AGENTS.md`. Keep the team's existing `AGENTS.md` content and its pasted "Vilnius dev standard" section; add the routing table and the documentation rules.
4. Copy [docs-check.yml](templates/docs-check.yml) to `.github/workflows/docs-check.yml` unless the repository already runs a link checker.
5. Run the **review pass**, then the **checker**.
6. Put the **Facts to confirm** list in the pull request description.

## Update

1. List the changed files: `git diff --name-only origin/main...HEAD` (use the base branch the user names, if any).
2. Match them against the source-paths column of the coverage table in `docs/README.md`. Every matching doc is affected.
3. Also check: new or renamed domain terms (glossary), API changes (regenerate the API spec with the repository's command), new commands or environment variables (`AGENTS.md`, README, deployment docs), and whether the change is a decision that needs an ADR (10.4: new technology, architecture style, integration model, significant trade-off, deviation from the standard).
4. Update every affected doc in the same branch. A changed area with no coverage row gets a row.
5. Run the **review pass** on the changed docs, then the **checker**.
6. Report which docs you changed and why, or which coverage rows you checked and why none needed a change.

## Audit

1. For each doc under `docs/`, plus README and `AGENTS.md`, verify claims against the code: every claim in docs under about 200 lines, otherwise every table row and a sample of at least ten claims per section.
2. Compare the docs against the layout table above and the maturity level in appendix G.3; list missing artifacts.
3. Check the coverage table: every source path exists, and every top-level source folder is covered or listed as a gap.
4. Run the **checker**.
5. Report findings one per line, grouped as Wrong, Missing, Stale and Checker: `path: problem (evidence: file and symbol)`. End with the **Facts to confirm** list. Change files only when the user asks.

## Review pass

Every mode ends with an independent re-check of the changed docs. Where your tool can start a sub-agent (Claude Code, Codex), give a fresh one the changed docs and this checklist; it reports problems and you fix them. Otherwise, after writing, reread each changed doc as a separate pass against the same checklist:

- Every cited path exists and contains the named symbol.
- Every behaviour claim matches the code: route paths, status codes (401 vs 403), queue and exchange names, which guards exist.
- No line numbers, no plans stated as facts, no fact kept in two docs.
- Every link resolves; docs that do not exist yet are plain text.
- Every domain claim is either proven by code behaviour or on the Facts to confirm list.

## Checker

Run from the repository root:

```bash
python3 .agents/skills/dev-standard-docs/check-docs.py
```

It checks README.md, AGENTS.md and `docs/` (pass paths to check others) for dead relative links, anchors with no matching heading, links or paths pointing at line numbers, and backticked paths under a top-level folder that do not exist. Fix every error it reports; it exits 0 when the docs are clean.

## Facts to confirm

Bootstrap and audit end with this section in the pull request description:

```markdown
## Facts to confirm

- [ ] `docs/glossary.md`, "Avilys (DVS)": the municipality's document management system. Inferred from `src/Service/Avilys/`.
```

One line per claim: the doc, the claim, and what you inferred it from.
